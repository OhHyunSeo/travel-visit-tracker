## 기존 사진 API를 그대로 연결하지 않은 이유

기존 서버의 `POST /api/photos`는 파일과 지역 ID만 받습니다. 서버가 사진 UUID를 새로 만들며, 모바일 사진 UUID·방문 UUID·전송 작업 UUID를 받지 않습니다. 서버 저장 뒤 응답을 놓쳐 다시 요청하면 사진이 하나 더 생길 수 있습니다. 기존 사진에는 방문 연결이 없으므로 같은 지역이라는 이유로 특정 방문에 붙이지 않습니다.

기존 지역 사진 API가 ‘원본’이라고 부르는 파일은 JPEG 품질 90으로 재인코딩한 파일입니다. 새 방문 사진 API는 첨부 바이트 그대로 저장하고 썸네일만 따로 만듭니다. 반면 앱은 JPEG·PNG 외에 HEIC·WebP 확장자의 첨부본도 보관할 수 있어 형식 지원 범위가 다릅니다.

방문을 삭제하면 앱은 연결된 사진과 전송 대기를 지우고 파일을 정리합니다. 서버의 기존 사진에는 방문 연결이 없어 방문 삭제와 함께 조회를 막을 수 없습니다. 따라서 새 사진 전송은 방문 삭제 처리와 함께 설계해야 합니다.

## 어떤 파일을 보존할까요?

권장 계약은 **앱의 영속 폴더에 저장된 첨부본을 그대로 백업하고 복원하는 것**입니다. 사진 선택 단계에 품질 0.85 옵션이 있으므로 이 첨부본을 카메라·사진 보관함 원본의 무손실 사본이라고 안내하지 않습니다.

- 서버는 받은 첨부본의 실제 바이트 해시·크기·형식을 확인하고 원본 첨부본과 썸네일을 별도로 저장합니다. 썸네일을 만들어도 첨부본을 덮어쓰지 않습니다.
- 전송·실패·재시도·로그아웃만으로 로컬 첨부본을 바꾸거나 삭제하지 않습니다. 전송 완료도 로컬 파일 삭제의 근거로 삼지 않습니다.
- 첫 단계에서 JPEG·PNG만 지원한다면 HEIC·WebP는 미지원 상태와 대기를 남깁니다. 이를 조용히 JPEG로 바꾸거나 사진 전체 백업 완료로 표시하지 않습니다. 형식 확대는 실제 디코더와 복원 검사를 통과한 뒤 진행합니다.
- 변환본을 백업하는 방식을 별도로 선택한다면 원본 첨부본은 유지하고, 변환본만 복원된다는 점을 안내해야 합니다. 재시도 때마다 새로 변환하지 않고 고정한 파일과 해시를 사용합니다.

이번 서버 구현에서도 기존 사진이나 파일을 변환·삭제하지 않았습니다. 부모 삭제 뒤 새 사진 경로의 조회는 차단하지만, 보관 파일의 물리 삭제·운영 정리 정책은 별도입니다.

## 저장과 전송의 약속

기존 지역별 사진 테이블·파일·API는 보존합니다. 방문에 연결된 사진은 별도 테이블과 API로 시작하는 편이 안전합니다. 새 테이블은 계정과 사진 UUID를 함께 식별하고, 같은 계정의 방문 UUID에 연결합니다. 생성 시각, 파일 해시·크기·형식, 저장 위치와 변경 순서도 기록합니다. 지역은 부모 방문에서 확인합니다.

새 업로드 요청에는 고정된 사진 UUID, 방문 UUID, 전송 작업 UUID와 생성 시각을 포함합니다. 기기 안의 파일 경로를 서버 메타데이터로 보내지 않습니다. 서버는 로그인 토큰으로 계정을 정하고 다음을 보장해야 합니다.

1. 같은 작업 ID와 내용은 같은 결과로 응답합니다. 다른 내용으로 재사용하면 409로 거절합니다. 응답 유실 뒤 같은 UUID·파일로 재시도해도 사진·처리 영수증이 늘지 않아야 합니다.
2. 먼저 전송된 방문이 같은 계정의 활성 GPS 방문인지 확인합니다. 부모 삭제가 먼저 처리됐다면 늦은 업로드로 사진을 되살리지 않습니다. 삭제된 방문의 원본·썸네일 조회도 막습니다.
3. 파일은 검증한 뒤 요청별 새 경로에 독점 생성합니다. 필요한 파일과 DB·처리 영수증이 준비된 뒤에만 성공 응답을 보냅니다. 파일시스템과 SQLite가 하나의 트랜잭션인 것처럼 가정하지 않습니다.
4. 실패 정리는 그 요청이 만든 미등록 파일만 대상으로 합니다. 커밋 여부를 다시 확인할 수 없으면 파일을 보존합니다. 기존 파일·다른 요청의 파일·소유권을 알 수 없는 예전 파일은 임의로 지우지 않습니다. 중간 종료 뒤 미참조 파일의 운영 복구 정책은 앞으로 마련해야 합니다.

클라이언트는 방문 전송을 먼저 처리한 뒤 사진 큐를 읽습니다. 사진 ACK는 요청 당시 계정·토큰·작업 ID·내용이 그대로일 때만 반영하며, ACK와 원격 메타데이터 저장을 한 트랜잭션으로 처리합니다. 계정 전환 뒤 늦게 온 응답으로 다른 계정의 큐나 파일을 바꾸지 않습니다. 사진 대기·미지원·오류와 방문 전송 완료를 구분합니다.

현재 자동 방문 백업 동의에는 사진을 보내지 않는다고 적혀 있습니다. 이 설정만으로 사진 전송을 시작하지 않고, 사진 전송 범위와 형식·복원 범위를 안내하는 동의를 먼저 연결합니다.

## 복원 전에 바꿔야 할 것

예전 모바일 v1/v2는 방문·사진·전송 작업의 UUID 하나를 전역 기본키로 사용했습니다. v3에서는 서버처럼 `(계정, UUID)`로 구분하고 사진·전송 메타데이터의 부모도 같은 계정에 연결합니다. 기존 행·URI·전송 내용과 시도 횟수를 한 트랜잭션으로 보존하며 실패하면 버전까지 되돌립니다. 게스트 가져오기는 부모 계정 변경에 따라 사진·메타데이터를 함께 옮기고, 대상 계정과 ID·세션이 겹치면 양쪽을 보존한 채 중단합니다. 이 갱신의 합성 검사와 iPhone/Android 각각의 native 24개를 통과했습니다.

복원은 인증된 메타데이터 목록과 다운로드 대기를 먼저 저장하고, 파일을 임시 위치에 내려받아 해시를 확인한 뒤 확정하는 흐름으로 만듭니다. 방문 연결·사진 행·처리 커서도 함께 저장해 중단 후 이어갈 수 있어야 합니다. 기존 로컬 첨부본을 원격본으로 교체하지 않으며, 이미 삭제된 부모 방문에 사진을 다시 붙이지 않습니다.

### 다음 구현에서 지킬 순서

1. **v3 구현·합성/양쪽 native 검사 완료:** 방문·사진·전송 작업·메타데이터의 키·외래키를 계정과 UUID로 함께 구분한다. 계정 A와 B에 같은 UUID가 있어도 각 계정의 부모 방문·사진·큐만 조회하고 갱신해야 한다. 기존 행·URI·작업 내용·재시도·설정은 하나의 DB 갱신 트랜잭션으로 보존한다.
2. 방문 변경사항과 삭제를 먼저 읽고 사진 목록·다운로드 대기를 별도로 저장한다. 로컬 삭제나 아직 보내지 않은 변경을 원격 목록만으로 덮어쓰지 않는다. 내려받기가 끝났다는 이유로 로컬 전송 큐를 지우지 않는다.
3. 새 파일명은 다른 계정의 같은 사진 UUID나 기존 첨부본과 충돌하지 않도록 만든다. 서버의 기기 경로·임의 URL을 그대로 쓰지 않고 확인된 서버의 인증된 사진 경로만 요청한다. 현재 attachment 파일명·폴더 검증도 유지한다.
4. 임시 파일의 JPEG/PNG 바이트·최대 크기·해시를 확인하고, 같은 계정·토큰·부모 방문이 유효할 때만 사진 연결·원격 메타데이터·처리 위치를 함께 저장한다. 파일과 SQLite가 한 트랜잭션인 것처럼 가정하지 않는다. DB 커밋 여부가 불확실한 파일은 보존한다.
5. 중단·다시 실행·잘못된 해시·파일 저장 실패·계정 전환·동일 UUID·삭제된 부모를 합성 자료로 먼저 검사한다. 기존 v1/v2 자료 보존과 새 합성 기기 DB의 첨부본 해시 일치까지 확인한 뒤 양쪽 native 파일·재실행 검사를 진행한다.

v4에 수동 다운로드·대기 보존과 재개를 연결했습니다. 새 복원의 합성·임시 HTTP 결과와 양쪽 native·화면 결과는 구분하며, 후자는 최신 진행 기록을 확인합니다.

### 내려받기를 연결할 때 확인할 점

서버에는 방문 생성보다 먼저 도착한 삭제 표시도 있습니다. 이 응답은 지역·세션·방문 시각이 비어 있을 수 있으므로 가짜 방문을 만들지 않고 삭제 상태를 별도로 보존해야 합니다. 기기에 없는 지역 ID도 임의의 지역에 연결하지 않습니다. 처리하지 못한 항목을 남기지 않은 채 조회 위치만 넘어가면 기록을 잃을 수 있습니다.

목록을 받은 뒤에는 다운로드 대기와 조회 위치를 같은 DB 트랜잭션으로 저장합니다. 파일을 받은 뒤에는 검증한 사진 연결·메타데이터 저장과 해당 대기 제거를 함께 처리합니다. 조회 위치와 파일 저장 완료를 구분해야 앱이 중간에 종료돼도 이어갈 수 있습니다. 아직 보내지 않은 로컬 변경·삭제와 기존 사진 파일은 이 과정에서 덮어쓰거나 지우지 않습니다.

## 작은 단위로 진행하기

1. **서버 기반 완료:** 방문 연결 사진·멱등 작업·첨부본 보존·인증된 조회·부모 삭제 차단과 기존 자료를 보존하는 DB v3을 구현했습니다.
2. **서버 합성 검사 완료:** 실제 임시 서버·SQLite·합성 이미지로 원본 바이트, 응답 유실·중복·삭제 경합·파일 실패·불확실한 커밋을 확인했습니다. 모바일·운영 복원 시험은 포함하지 않습니다.
3. **수동 클라이언트 구현·합성 검사 완료:** 방문 선행, 계정·foreground 가드, 고정 해시·작업 UUID와 원자적 ACK를 연결했습니다. 비동기 파일 복사를 기다리고 전송용 사본만 정리합니다. 양쪽에서 각각 native 파일 준비1개·별도 SQLite/실HTTP 통합9개 PASS입니다.
4. **화면과 동의 구현:** 매번 대상 계정·서버·전송 범위를 확인하고 수동으로 보냅니다. 전송 대기·서버 저장 확인 수와 건너뛴 사유를 구분합니다. Android 빈 계정 확인창과 양쪽 사진1건의 확인·전송·매 실행 재확인 PASS입니다. 방문만 완료된 상태를 전체 백업 완료라고 쓰지 않습니다.
5. **복원:** 키 충돌을 해결하는 모바일 DB 갱신과 다운로드·재개를 구현하고, 새 합성 기기 DB에서 복원합니다. 마지막으로 양쪽 플랫폼의 별도 테스트 기기에서 검증합니다.

완료 여부를 판단할 검사는 다음과 같습니다.

- 같은 작업 동시 요청, 서버 저장 후 응답 유실, DB 재개방 뒤 같은 UUID 재전송에서 사진·영수증 중복 없음
- 같은 UUID에 다른 바이트·방문 연결을 넣으면 거절, 타계정 원본·썸네일·목록 접근 차단
- 부모 삭제 전후의 업로드·조회와 오래된 요청 재전송에서 삭제가 되살아나지 않음
- 계정·토큰 전환 중 지연 응답, 자동 전송 해제, 재시도에서 큐·파일·메타데이터 격리
- 파일 쓰기·썸네일 생성·DB 저장 실패와 중간 종료 후에도 기존 파일 보존 및 안전한 재시도
- 다운로드 중단·해시 불일치·공간 부족에서 잘못된 파일을 확정하지 않고 대기 보존
- 기존 계정·사진·URI·큐를 유지하는 DB 갱신, A/B 동일 UUID 충돌, 새 테스트 DB 복원 후 첨부본 해시 일치

자동 검사나 JS 번들 생성만으로 실제 휴대폰 복원을 통과 처리하지 않습니다. 양쪽 기기의 파일·썸네일 표시와 중단·재개까지 확인한 범위를 따로 기록합니다.
