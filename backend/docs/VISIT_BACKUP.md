# 방문을 서버에 백업하기

앱이 같은 방문을 여러 번 보내거나, 삭제 요청이 먼저 도착해도 결과가 달라지지 않게 만드는 API입니다. 앱의 수동 방문 백업과 선택적인 자동 백업에 연결했습니다. 아래 예시는 개발용 합성 자료입니다.

## 앱에서 백업하기

계정 화면의 **방문 백업하기**로 방문과 방문 삭제 요청을 보냅니다. 자동 방문 백업은 계정마다 기본 꺼짐이며, 안내에 동의한 뒤 켤 수 있습니다. 앱이 화면에 열려 있을 때 시작·화면 복귀·4초마다의 점검에서 전송을 요청합니다. 연결에 실패하면 다음 시도 시각을 기기에 저장해 재실행 뒤에도 지키며, 재시도 간격은 30초에서 최대 5분입니다.

연결 전송 오류에는 다음 연결 확인 시각도 기기에 저장합니다. 앱이 열린 동안 약 30초 간격의 due 확인에서 설정한 서버의 `/health`를 최대 3초 동안 확인합니다. 이 요청에는 인증값·방문 내용을 보내지 않습니다. 서버 연결이 복구되면 계정·토큰·동의·중단 상태와 이전 retry/check 시각이 맞을 때만 긴 retry 대기를 풀고 같은 작업을 보냅니다. OS 네트워크 복귀 이벤트를 감지하는 방식은 아닙니다. HTTP500 같은 서버 오류의 재시도나 아래 인증·충돌 중단은 이 확인으로 우회하지 않습니다.

401 인증 오류와 409 충돌은 자동 재시도를 멈춥니다. 다시 로그인하거나 충돌을 확인한 뒤 수동으로 재시도할 수 있습니다. 마지막 완료 시각은 실제 방문 ACK를 받은 뒤 방문 대기 목록이 비었을 때만 저장합니다. 대기 수는 고유 방문 수가 아니라 방문 변경사항 수이며 사진 작업은 따로 남깁니다. 사진 업로드와 기기의 기록 복원은 아직 연결하지 않았습니다.

## 방문 보내기

`POST /api/visits/sync`에 로그인 토큰과 `operations` 배열을 보냅니다. 한 요청에 최대 100개이며 빈 배열도 받을 수 있습니다. 계정은 토큰에서 정하므로 요청에 사용자 ID를 넣지 않습니다.

```json
{
  "operations": [{
    "id": "00000000-0000-4000-8000-000000000001",
    "entityType": "visit",
    "entityId": "00000000-0000-4000-8000-000000000001",
    "operation": "upsert",
    "payload": {
      "id": "00000000-0000-4000-8000-000000000001",
      "sessionId": "00000000-0000-4000-8000-000000000002",
      "regionId": "gb:synthetic-test-region",
      "startedAt": 1700000000000.25,
      "confirmedAt": 1700000300000.5,
      "source": "gps",
      "deletedAt": null
    }
  }]
}
```

시각은 Unix 밀리초이며 소수점도 보존합니다. 5분 이상 체류한 GPS 방문만 받으며, 개발용 방문은 보내지 않습니다. 지역 ID는 최대 160자의 영문, 숫자, `:`, `.`, `_`, `-`를 사용합니다. 서버가 GPS 원본을 확인하는 것은 아니므로 이 검사만으로 실제 방문을 인증했다고 보지 않습니다.

저장을 마친 응답은 다음과 같습니다.

```json
{ "acknowledgedIds": ["00000000-0000-4000-8000-000000000001"] }
```

응답이 유실되면 **같은 작업 ID와 내용**으로 재시도합니다. 같은 ID에 다른 내용을 넣거나 확정 방문의 지역·시각을 덮어쓰려 하면 409를 돌려줍니다. 한 묶음의 어느 작업이든 실패하면 방문, 삭제와 처리 기록을 모두 롤백합니다.

기기는 성공 응답의 ID와 일치하는 작업만 전송 대기 목록에서 확인합니다. 모바일 서비스는 전송 당시의 ID·내용·계정과 일치하는 방문 작업만 처리하고 사진 작업은 남깁니다. 계정이나 토큰을 바꾼 뒤 도착한 응답도 큐를 바꾸지 않습니다. 이 동작은 임시 DB와 합성 자료로 검사했습니다. ACK는 작업 처리가 끝났다는 뜻이며 현재 방문이 활성이라는 뜻은 아닙니다. 아래 내려받기 응답으로 최종 상태를 확인합니다.

## 삭제 보내기

새 작업 UUID를 만들고 `operation`을 `delete`로 지정합니다. `entityType`, `entityId`는 유지하고, `payload`에는 `id`와 `deletedAt`만 넣습니다. 이 작업도 `operations` 배열 안에 넣어 보냅니다.

```json
{
  "id": "00000000-0000-4000-8000-000000000003",
  "entityType": "visit",
  "entityId": "00000000-0000-4000-8000-000000000001",
  "operation": "delete",
  "payload": {
    "id": "00000000-0000-4000-8000-000000000001",
    "deletedAt": 1700000400000
  }
}
```

삭제 표시는 보존하며 예전 `upsert`가 도착해도 되살리지 않습니다. 원래 방문보다 삭제가 먼저 도착했다면 시각·지역 정보가 없는 삭제 표시를 저장합니다. 내려받는 쪽은 먼저 `deletedAt`을 확인해야 합니다. 계정별 사진 API와 방문에 연결된 사진의 삭제·복원 흐름은 아직 통합하지 않았습니다.

## 방문과 삭제 상태 내려받기

`GET /api/visits?after=0&limit=100`에서 시작합니다. 응답은 `visits`, `cursor`, `hasMore`를 포함합니다. 각 방문에는 `revision`이 있고, 삭제된 방문도 반환합니다. 다른 계정의 자료는 포함하지 않습니다.

`hasMore`가 true면 다음 요청의 `after`에 응답 `cursor`를 넣습니다. limit은 1~500이며 기본 100입니다. 이후 변경을 가져올 때에도 마지막으로 처리한 cursor를 사용합니다. 비어 있는 응답은 입력 cursor를 유지합니다. 조회 결과는 현재 상태를 나타내며 특정 시점의 고정 스냅샷은 아닙니다. 기기의 커서 저장·복원과 여러 기기 병합 검증은 후속 작업입니다.

## 검사하기

```sh
npm --prefix backend test
```

임시 서버와 DB로 동시 재전송, 다른 계정의 같은 UUID, 삭제가 먼저 도착한 경우, 전체 롤백과 재개방을 확인합니다. 실제 사용자 DB와 사진은 시험에 사용하지 않습니다.

저장소 루트의 `bash scripts/verify-cloud.sh`는 모바일 서비스와 이 서버를 함께 검사합니다. 임시 모바일·서버 DB에서 응답 유실 뒤 재개방·재전송, 사진 큐 보존, 계정 전환과 삭제 재전송을 확인합니다.
