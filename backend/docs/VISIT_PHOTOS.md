# 방문에 연결된 사진 백업 API

2026-10-18 서버 기반과 앱의 수동 사진 전송·전용 확인창을 연결했습니다. 앱의 자동 방문 백업 동의는 방문만 포함하며 사진 전송은 매번 계정·서버를 확인한 뒤 실행합니다. **파일 다운로드·다른 기기 복원과 사진 자동 전송은 아직 없습니다.** 실제 임시 HTTP·SQLite·합성 첨부본 검사와 양쪽 JS 번들까지 통과했고 새 native 사진 전송·화면 검증은 남아 있습니다.

기존 `POST /api/photos`와 지역별 사진·파일은 그대로 보존합니다. 새 경로는 로그인한 계정의 방문 UUID에 사진을 연결하고, 앱이 보관한 JPEG·PNG 첨부본 바이트를 그대로 저장합니다. 사진 선택 전에 있던 카메라 원본까지 무손실이라는 뜻은 아닙니다.

## 사진 보내기

`POST /api/visit-photos`에 `Authorization: Bearer <access-token>`을 넣고 multipart로 보냅니다.

| 필드 | 값 |
| --- | --- |
| `file` | JPEG 또는 PNG 한 개. 최대 10MiB, 총 2,500만 픽셀 |
| `id` | 기기에 저장된 사진 UUID |
| `visitId` | 먼저 전송된 같은 계정의 활성 GPS 방문 UUID |
| `operationId` | 재시도 때에도 유지할 전송 작업 UUID |
| `createdAt` | Unix 밀리초 문자열. 0 이상·MAX_SAFE_INTEGER 이하의 유한 수, 소수점 허용 |

UUID는 대소문자를 받아 소문자로 정규화합니다. 계정·지역·파일 경로를 추가 필드로 보내지 않습니다. 계정은 토큰에서, 지역은 부모 방문에서 확인합니다. HEIC·WebP와 다른 형식은 아직 받지 않으며 원본 첨부본을 몰래 변환하지 않습니다. 실제 파일 형식과 MIME도 검사합니다.

성공 응답 예시는 합성 자료입니다.

```json
{
  "acknowledgedId": "00000000-0000-4000-8000-000000000003",
  "photo": {
    "id": "00000000-0000-4000-8000-000000000001",
    "visitId": "00000000-0000-4000-8000-000000000002",
    "createdAt": 1700000300000.25,
    "sha256": "<첨부본의 SHA-256>",
    "byteLength": 1234,
    "mimeType": "image/png",
    "revision": 1,
    "originalPath": "/api/visit-photos/00000000-0000-4000-8000-000000000001/original",
    "thumbnailPath": "/api/visit-photos/00000000-0000-4000-8000-000000000001/thumbnail"
  }
}
```

경로는 같은 서버에 대한 상대 경로이며 조회할 때도 인증 헤더가 필요합니다. 썸네일은 방향을 반영한 200×200 JPEG 파생 파일입니다. 첨부본은 그대로 두고 서버가 실제 바이트의 해시·크기를 계산합니다.

## 재시도와 충돌

서버 저장 뒤 응답을 놓치면 **같은 사진·방문·작업 UUID, 생성 시각과 첨부 파일**로 재시도합니다. 같은 작업·내용은 같은 ACK를 반환하며 파일·사진·변경 이력을 늘리지 않습니다. 새 작업 UUID로 같은 사진과 내용을 보내면 기존 파일을 사용하고 처리 영수증만 추가합니다.

이미 쓴 작업 UUID나 사진 UUID에 다른 내용·방문·시각을 넣으면 409입니다. 다른 계정은 같은 UUID를 독립적으로 사용할 수 있고 서로의 사진을 읽을 수 없습니다. 없는 부모나 다른 계정의 부모는 404, 삭제된 부모는 409입니다. 부모가 삭제되면 예전에 성공했던 작업을 다시 보내도 사진을 되살리거나 성공 응답으로 우회하지 않습니다.

파일은 요청마다 새 이름으로 독점 생성하고 DB·영수증이 커밋된 뒤 ACK합니다. 실패 정리는 그 요청이 만든 미등록 파일만 대상으로 합니다. 커밋 결과가 불확실하면 등록된 원본·썸네일은 보존하며, DB 재조회까지 실패하면 파일을 남깁니다. 파일시스템과 SQLite가 하나의 트랜잭션인 것은 아니므로 프로세스 중간 종료의 미참조 파일 정리·운영 복구는 별도 작업입니다. 기존 파일이나 소유권을 모르는 파일을 일괄 삭제하지 않습니다.

## 목록과 다운로드

`GET /api/visit-photos?after=0&limit=100`은 같은 계정의 활성 부모에 연결된 사진을 revision 순서로 반환합니다.

```json
{ "photos": [], "cursor": 0, "hasMore": false }
```

`hasMore`가 true면 응답 cursor로 이어갑니다. limit은 1~500이며 빈 응답은 입력 cursor를 유지합니다. 현재 목록은 살아 있는 사진 조회용입니다. 사진 자체 삭제 feed나 여러 기기의 복원 커서 저장은 구현하지 않았으며 방문의 삭제 상태는 방문 API에서 확인해야 합니다.

`GET /api/visit-photos/:id/original`, `GET /api/visit-photos/:id/thumbnail`은 같은 계정과 활성 부모를 다시 확인합니다. 다른 계정·삭제된 부모·없는 파일은 404이며, 응답은 `private, no-store`와 `nosniff`를 사용합니다. 서버 파일명과 모바일의 기기 경로는 응답하지 않습니다.

## DB 갱신과 검사 범위

서버 DB 버전 3은 `visit_photos`, `visit_photo_changes`, `photo_sync_operations`를 추가합니다. 기존 계정·여행·위치점·지역 사진·방문·삭제 표시·전송 영수증은 유지합니다. 사진 키는 `(계정, 사진 UUID)`, 부모 연결도 같은 계정의 방문을 참조합니다. 기존 사진을 지역명만 보고 방문에 붙이지 않습니다.

`npm --prefix backend test`는 임시 서버·DB·합성 이미지로 원본 바이트·썸네일 디코딩, 동시 중복·응답 유실·재개방·불변성 충돌·계정 격리·부모 삭제·한계값·파일/DB 실패와 버전 0·1·2→3 보존을 검사합니다. 이 결과를 앱 사진 백업·실제 휴대폰 복원·운영 서버 배포 완료로 표시하지 않습니다. [모바일까지 연결할 순서](../../docs/PHOTO_BACKUP_PLAN.md)를 참고하세요.
